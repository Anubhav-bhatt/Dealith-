# Deal state machine

Status: frozen architecture, 2026-09-06. Source: master §33 and Phase 0 §14. Exactly **28 states**: 22 lifecycle states and 6 exit/interruption states. `DISPUTED` is an interruption with explicit recovery; it is not necessarily terminal. The [lifecycle registry](architecture/LIFECYCLE_REGISTRY.json) is the complete allowlist.

Creation starts at INQUIRY with deal.create and emits deal.created. One Deal has one project, a snapshotted DealTypePolicy and identified buyer/seller principals. Creation and requestAccess can compose INQUIRY → ACCESS_REQUESTED in one transaction and record both events. Phase 6 introduces this minimal kernel; Phase 9 implements offers and the remaining engine. A Deal Cart item never shares a settlement with another Deal.

All edges require explicit actor capability plus ABAC, current expectedVersion, invariant checks in one transaction, DealEvent, AuditEvent and outbox. All emit deal.transitioned; business events listed below are additional. A command names an intent (acceptOffer, confirmFunding), never an arbitrary target supplied by a browser. Repeated valid commands replay their stored result; stale versions return a safe conflict. Same-state counters, messages, NDA renewals and milestone updates use their own immutable entities and events without inventing self-transitions.

Access/NDA/verification/grants remain independent live predicates. Reaching NDA_SIGNED once does not authorize future reads after expiry or removal. Renewal updates NdaVersion and current signer evidence without rewinding a late-stage deal. Access revocation imposes a command/policy hold; serious disagreements use DISPUTED. No lifecycle state grants permission by itself.

V1 enabled executable transactions require positive provider-managed fiat escrow settlement. Full/partial asset purchases, code/IP purchases and supported licensing have versioned participant, LOI, diligence, agreement, settlement and transfer templates. No-money partnerships, revenue-share automation, contingent earn-outs, convertible instruments, regulated investments and crypto remain discoverable only where separately approved policy permits, with execution off until an ADR adds tested settlement/rights policies. LOI may be waived only by explicit DealTypePolicy and both parties; diligence/agreements/escrow/inspection are never silently skipped. Milestones exist inside Settlement, but ESCROW_FUNDED means the required pre-transfer funding threshold is met and SETTLED means every final liability is reconciled. No release before applicable milestone acceptance. V1 baseline uses one fully funded milestone; more complex schedules are capability-gated.

REJECTED, WITHDRAWN, EXPIRED, CANCELLED and FAILED are terminal deal records. A fresh attempt creates a linked new Deal, not a history rewrite. CLOSED is operationally complete but may enter DISPUTED for a post-close claim. Historical settlement, portfolio provenance, signatures and transfer evidence remain true; a dispute does not reverse a payment. Recovery requires both an approved resolution and reconciliation of actual provider effects. Provider event arrival time is not a lifecycle ordering rule. If an already-in-flight release completes while disputed, persist its financial truth while retaining the hold, then resolve through the explicit guarded target edge.

The cancellation edges below run only after funds and contractual rights are resolved. A request to cancel first creates a hold and refund/cancellation operation while keeping the current state (or DISPUTED if contested); the eventual authoritative outcome permits CANCELLED. Manual users cannot assert refunds, funding or release. A provider outage or timeout remains pending/unknown and cannot satisfy FAILED. This preserves visibility of stranded money and obligations.

## Concurrency and verification

The domain command locks or compares the aggregate version, checks current grants and restrictions within the transaction, writes immutable transition history and audit, and appends the outbox record. Cross-module critical commands use exported services and a shared transaction coordinator, never foreign-table writes. External I/O runs after durable intent through workers. Consumers do not bypass guards. Financial/rights reservations require unique constraints and serializable retry where multiple aggregates race.

Phase 0 validation checks unique edges, exact canonical state sets, reachability, adjacency parity, nonempty actor/permission/guard/event contracts and named event registration. Phase 9 must test every listed edge and every unlisted ordered state pair, including stale versions, insufficient permission and failed guards; Phase 3 tests project transitions. Runtime evidence is not claimed in Phase 0.

Event ownership follows [DOMAIN_EVENTS](DOMAIN_EVENTS.md): additional edge events are facts emitted once by the owning module in the coordinated transaction, or already committed causal facts consumed by this transition. The lifecycle owner emits its transition event and must not re-emit a consumed Access/NDA/Settlement fact. Event receipt never bypasses the edge guard.

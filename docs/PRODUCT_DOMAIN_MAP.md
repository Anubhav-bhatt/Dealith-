# Product domain map

Status: Phase 0 architecture freeze. Primary specification: [master scope](../DEALITH_MASTER_PROJECT_SCOPE.md), especially sections 4–47, 51–54 and 88. This catalog covers all **51 named product domains**. A domain row does not imply a service or a separate NestJS module: related subdomains share an aggregate owner as recorded below.

The API is a modular monolith. A module owns writes to its tables; other modules call its application interface or consume versioned events. Public interface below means the authenticated HTTP resource group and the equivalent internal port, not unrestricted public access. `P` denotes delivery phase; `kernel` means the minimum security/workflow dependency, with the fuller product experience later. Architecture for every row is frozen in Phase 0; implementations remain gated by [phase acceptance](PHASE_ACCEPTANCE_MATRIX.md).

## Cross-domain rules

The named Authorization infrastructure owner additionally owns `RoleAssignment` and `PolicyBinding`; Privacy infrastructure owns `ConsentRecord` and `PrivacyRequest`; Platform Reliability owns `OutboxEvent`, `ConsumerReceipt` and `IdempotencyRecord`. These support the 51 domains and do not add market-facing product scope. Every concrete entity is cataloged in [DATA_MODEL.md](DATA_MODEL.md).

Commands are explicit application methods with input, actor, expected aggregate version and policy context. Aggregate writes plus authoritative audit and outgoing event records commit together. A domain event is a past fact; consuming it never grants a new permission. Cross-module APIs return purpose-specific DTOs. Infrastructure retries cannot bypass business guards.

A transaction can span local domain repositories through a designated application coordinator when one invariant must be atomic, particularly accepted offer + deal stage + listing reservation. The coordinator calls owner repositories through declared interfaces; controllers do not import another module's Prisma model. Provider calls run outside database transactions using durable `ProviderOperation` records. Extracting a module later replaces a local port with a contract, and replaces cross-module transactions with an explicit reservation/compensation protocol in an ADR before extraction.

## Product boundaries and lifecycle dependencies

The catalog models all master-scope asset and deal types. Only individually enabled, fully governed `DealTypePolicy` versions may be transacted. The first complete reference flow is provider-managed acquisition escrow in sandbox. Licensing, partnership and investment variants need explicit document, diligence, transfer, currency/jurisdiction and provider-capability rules before activation. A nonexclusive license preserves seller rights; closing it does not mark the entire listing SOLD. Regulated investments and crypto remain off pending separate compliance/provider gates; convertible instruments remain future scope.

Phase 6 creates the minimal `Deal`, participants and auditable `INQUIRY`/access-stage history before access or communication. Phase 9 expands the same aggregate; it does not migrate unrelated access/messaging records into a new deal after the fact. Before Phase 8, NDA-required disclosure fails closed and the UI records that the capability is not yet available. Phase 3 includes the minimum ownership/reviewer and file-safety controls needed by publishing; these cannot wait for Phases 7/13. Phase 11–12 money and completion workflows remain in sandbox until Phase 15 launch approval.

Deal Cart and Watchlist never reserve a listing or create an obligation. Comparison is a view over separately authorized listings; choosing one calls `DealPort.inquire` or `AccessPort.request` with an idempotency key and creates/returns one independent deal. No cart-wide settlement exists.

## Public discovery projection

Use PostgreSQL text search and indexed structured filters initially. `SearchProjection` contains only approved public fields, coarse financial bands, evidence labels and safe ranking features. Private exacts, customer names, source code and document text never enter this public index. An index removal event reduces stale exposure; API eligibility checks are still required on each result. Search caches partition by safe public eligibility dimensions and never contain confidential personalized query output.

Deterministic ranking is the fallback for recommendations and comparison. Semantic search is a Phase 7 capability behind a feature flag and an offline relevance/performance gate; evaluate a PostgreSQL vector extension before selecting a supported version in implementation. OpenSearch is deferred until measured search scale or relevance requirements justify extraction. Search provider interfaces, filter AST, cursor semantics, safe source fields and benchmark requirements are frozen now; vendor/version configuration is an implementation gate.
